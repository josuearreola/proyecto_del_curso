1. Descripción del Caso de Estudio

El proyecto UTEQGram surge de la necesidad de ofrecer a los estudiantes y docentes de la Universidad Tecnológica de Querétaro (UTEQ) una plataforma ágil, liviana y confiable para compartir vivencias y actividades institucionales. El campus cuenta con áreas donde la conectividad a internet móvil es inestable o nula.

Para dar solución a este reto, se diseñó e implementó una Progressive Web App (PWA) bajo una filosofía Offline-First. Esta arquitectura permite a la aplicación seguir operando plenamente sin conexión: los usuarios pueden visualizar publicaciones previamente almacenadas, navegar por las pantallas del sistema y redactar nuevos aportes que se resguardan de forma segura en una cola transaccional local para sincronizarse de manera transparente en cuanto la red vuelve a estar disponible.

2. Justificación de Plataformas y Herramientas Utilizadas

Para la construcción y puesta en marcha del proyecto se seleccionaron herramientas estándar de la industria que garantizan rendimiento, mantenibilidad y nula dependencia de empaquetadores complejos:

Plataforma / Herramienta Categoría Justificación Técnica
HTML5 / CSS3 / JavaScript (ES6) Frontend Base Uso de tecnologías estándar nativas de la web para máxima velocidad de carga, compatibilidad multiplataforma y cero sobrecarga de frameworks externos.
Material Design Lite (MDL) Diseño UI / UX Proporciona una interfaz visual profesional basada en los lineamientos Material Design de Google, con componentes adaptables a móviles (cajón de navegación, tarjetas, botones flotantes de acción y snackbars de notificación).
Service Worker API Arquitectura PWA Componente central que se ejecuta en un hilo separado al navegador. Intercepta el tráfico de red HTTP, gestiona el almacenamiento en caché de los activos estáticos (App Shell) y habilita el procesamiento en segundo plano.
IndexedDB (vía librería idb.js) Almacenamiento Local Base de datos transaccional NoSQL integrada en el navegador. Supera las limitaciones de localStorage (5MB y síncrono), permitiendo persistir objetos JSON estructurados de gran tamaño de manera asíncrona.
Background Sync API Sincronización Diferida Permite delegar peticiones de red al Service Worker mediante el evento sync, garantizando que el usuario no pierda su información al crear publicaciones sin señal.
Supabase (PostgreSQL & Storage) Backend as a Service (BaaS) Proporciona una base de datos relacional robusta accesible directamente mediante API RESTful segura con cabeceras de autorización y servicio de almacenamiento en la nube para recursos multimedia.
Vercel Hosting & Edge Network Plataforma de despliegue en la nube que suministra certificados SSL automáticos (HTTPS mandatorio para Service Workers y WebAPKs), CDN global para distribución de activos estáticos y entrega de baja latencia.
Git & GitHub Control de Versiones & CI/CD Control de versiones distribuido que facilita la trazabilidad de cambios y se conecta de manera continua con Vercel para despliegues automatizados en cada actualización de la rama principal.

3. Parámetros de Configuración de las Plataformas

3.1. Configuración de Despliegue en Vercel (vercel.json)

Para instruir a Vercel que sirva los activos estáticos y el Service Worker desde la raíz pública sin requerir pasos de transpilación, se definió: 

{
  "outputDirectory": "public",
  "cleanUrls": true
}
  • outputDirectory: "public": Indica a la red de Vercel que el directorio base de entrega es la carpeta public/, garantizando que /sw.js tenga alcance sobre la totalidad del origen /.
  • cleanUrls: true: Habilita el enrutamiento limpio de rutas amigables en el cliente.

3.3. Configuración del Service Worker y Estrategias de Caché (public/sw.js)

  • Control de versiones de caché: CACHE_STATIC_NAME = 'static-v10' y CACHE_DYNAMIC_NAME = 'dynamic-v10'. Garantizan la invalidación inmediata de recursos obsoletos en el evento activate.
  • Precaching (App Shell): En el evento install se precachean de manera atómica los archivos esenciales: index.html, offline.html, manifest.json, hojas de estilo CSS, librerías JavaScript e iconos.
  • Sincronización en segundo plano con Promise.all: El evento sync recorre el almacén sync-posts manteniendo vivo el Service Worker hasta confirmar la respuesta exitosa de Supabase: 
    self.addEventListener('sync', function (event) {
  if (event.tag === 'sync-new-posts') {
    event.waitUntil(
      readAllData('sync-posts').then(function (data) {
        return Promise.all(data.map(function (post) {
          return fetch(SUPABASE_URL + '/rest/v1/post', {
            method: 'POST',
            headers: { 'apikey': SUPABASE_KEY, 'Authorization': 'Bearer ' + SUPABASE_KEY, 'Content-Type': 'application/json' },
            body: JSON.stringify(post)
          }).then(function (res) {
            if (res.ok) return deleteItemFromData('sync-posts', post.id);
          });
        }));
      })
    );
  }
});

3.4. Configuración de Base de Datos y API en Supabase

  • Endpoint RESTful: https://xmmkfhtidsgyrebpmcij.supabase.co/rest/v1/post
  • Esquema de Tabla post: Campos id (text, primary key), title (text), location (text), image (text).
  • Cabeceras de Petición HTTP: apikey y Authorization: Bearer <ANON_KEY> para acceso autenticado de lectura e inserción sin restricciones indebidas de CORS.

4. Arquitectura de Pantallas, Vistas y Manejo de Datos

4.1. Pantallas y Home

  • Home / Feed Principal: Pantalla principal donde se renderiza la cabecera institucional, la imagen representativa del campus de la UTEQ, el botón flotante de publicación (+) y el contenedor dinámico de publicaciones.
  • Cajón Lateral de Navegación (Drawer): Menú colapsable adaptativo que permite desplazarse hacia el Feed, la pantalla de Ayuda y habilitar notificaciones push.
  • Modal de Creación de Publicación: Panel deslizante animado con inputs flotantes de Material Design para ingresar título y localización.
  • Pantalla de Respaldo Offline (offline.html): Vista de contingencia servida por el Service Worker ante fallos de red al solicitar páginas no cacheadas.

4.2. Vistas del Lado del Cliente (Client-Side Rendering - CSR)

La aplicación emplea renderizado dinámico en el cliente. El archivo JavaScript feed.js realiza la iteración de los registros (obtenidos de la API remota o de IndexedDB) y construye dinámicamente en el DOM los elementos correspondientes mediante createCard(data), aplicando los estilos de Material Design sin requerir recargas completas ni renderizado en servidor (SSR).

4.3. Gestión de Datos: Locales, Remotos y Offline

Ámbito Tecnología / Mecanismo Comportamiento Implementado
Remoto (Online) Supabase REST API (PostgreSQL) Al estar conectado, la aplicación consulta /rest/v1/post?select=* para obtener las últimas publicaciones compartidas por la comunidad universitaria.
Local (Caché de Lectura) IndexedDB (Almacén posts) Cada respuesta exitosa de la red actualiza de inmediato el almacén posts en el dispositivo del usuario. Si el usuario vuelve a abrir la app sin conexión, los datos se cargan al instante desde IndexedDB.
Offline (Cola de Escritura) IndexedDB (Almacén sync-posts) + SyncManager Si el usuario crea un post sin internet, los datos se resguardan en sync-posts y se registra el evento sync-new-posts. En cuanto la conectividad regresa, el Service Worker procesa la cola y la envía a Supabase.

7. Conclusiones

La implementación de UTEQGram demostró la efectividad de las Progressive Web Apps para entornos educativos con condiciones de red variables. Gracias a la combinación de Service Workers, IndexedDB y Background Sync, la aplicación brinda una experiencia de usuario idéntica a la de una aplicación nativa, eliminando la fricción de instalación por tiendas tradicionales y garantizando la integridad de los datos en todo momento.
